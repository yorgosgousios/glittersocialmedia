1. THE BIG PICTURE
=====================================================================

  developer laptop ──git push──▶ GitHub ──CI (lint + Docker smoke)──▶ Deploy
                                                                       │ FTPS (lftp)
                                                                       ▼
  visitors ──DNS (Papaki)──HTTPS──▶  Papaki / Plesk: WordPress + Polylang
                                     + "glitter" theme in wp-content/themes/glitter

  Only the THEME is version-controlled and deployed. WordPress core, plugins
  (Polylang, later WP Mail SMTP), uploads and the database live on the server
  and are managed through WP admin / Plesk WP Toolkit.

  Why theme-only: it is the only custom code; deploying core/plugins/DB from git
  on shared hosting is fragile and unnecessary. Content is edited by the agency
  in WP admin, so the database must never be overwritten by a deploy.

4. DEPLOYMENT (GitHub Actions)
=====================================================================

  ci.yml — every push and pull request:
  - PHP 8.1 and 8.3: syntax check + PHPCS (WordPress Coding Standards)
  - ESLint + Stylelint
  - Smoke test: fresh Docker WordPress → install (incl. Polylang + languages)
    → seed placeholders → key pages in both languages return 200, 404 works,
    PHP error log empty
  - Builds glitter-theme.zip artifact

  deploy.yml — after CI succeeds on main (or "Run workflow" manually):
  - Runs only while repo variable DEPLOY_ENABLED = true.
  - Uploads theme/ to /httpdocs/wp-content/themes/glitter/ with lftp over FTPS
    (mirror --reverse: only changed files; --delete: removes theme files that
    were deleted in git). Nothing outside the theme folder is touched.
  - Optional health check when PRODUCTION_URL is set.

  GitHub settings (repo → Settings → Secrets and variables → Actions):
    secrets   FTP_HOST       = linux72.papaki.gr   (server name; the cert is
                                                     *.papaki.gr, so not the domain)
              FTP_USERNAME / FTP_PASSWORD           (Plesk FTP user)
              FTP_THEME_DIR  = /httpdocs/wp-content/themes/glitter/
              FTP_TARGET_DIR (old Vite deploy; unused, can be deleted)
    variables DEPLOY_ENABLED = true
              PRODUCTION_URL — leave EMPTY until launch: the health
                               check expects 200, coming soon mode returns 503
              FTP_PROTOCOL   — optional, "ftp" disables TLS (not recommended)

  Why FTPS with lftp (and not the FTP-Deploy-Action):
  - The first deploy with SamKirkland/FTP-Deploy-Action (Node basic-ftp) logged
    in but failed with "ECONNRESET (data socket)": Plesk's FTPS requires TLS
    session reuse on data connections, which basic-ftp doesn't support.
  - Plain FTP would work but sends the password unencrypted on every deploy.
  - lftp supports session reuse, verifies the server certificate (*.papaki.gr,
    valid), reads the password from an env var (--env-password, safe for any
    characters) and only transfers changed files. Tested locally against an
    FTP server in Docker: 48/48 files on first run, 0 transfers on a re-run.

  Why the old Vite FTP workflow was removed: the repo used to hold a Vite/React
  "under construction" page deployed to httpdocs/dist. The project is now a
  WordPress theme; the old app and its workflow were deleted (history keeps them).

6. ONE-TIME SITE SETUP WITHOUT WP-CLI
=====================================================================

  Problem: the bilingual structure (languages, linked page translations, menus
  per language, permalinks) is created by code locally (`make install` via
  WP-CLI), but the server has no SSH/WP-CLI.

  Solution: the same code runs from WP admin → Appearance → "Ρύθμιση Glitter"
  (Glitter setup). One shared function, theme/inc/site-setup.php, used by:
    - the admin page (theme/inc/admin-setup.php) on production
    - scripts/setup.php locally (make install)
  It is idempotent (reuses existing pages/menus), publishes reused draft pages
  (e.g. WordPress's default Privacy Policy), trashes the untouched default
  "Sample page" / "Hello world", and writes .htaccess rewrite rules itself
  (WordPress doesn't load that helper during admin-post requests — this caused
  404s on every pretty URL until fixed).

  Production order used: install Polylang (skip its wizard) → upload/activate
  theme → Appearance → Ρύθμιση Glitter → Run.

7. WORDPRESS ARCHITECTURE & BILINGUAL DECISIONS
=====================================================================

  - Custom classic theme, no page builder: fast, fully controlled markup,
    nothing for the client to break; content via block editor + custom types.
  - Polylang (free) for languages:
      Greek = default at "/", English at "/en/" (directory mode, no
      /language/ prefix, no browser-language redirect, translated front page
      served at /en/ not /en/home/).
  - Greek pages use transliterated slugs (/sxetika/, /epikoinonia/, /nea/,
    /politiki-aporritou/) because Polylang free can't give two translations the
    same slug.
  - Greeklish slugs generated automatically for Greek titles
    («Τι κάνουν…» → /ti-kanoun-…/) instead of percent-encoded URLs.
  - Theme UI strings are translated with gettext files
    (theme/languages/el.po → el.mo + el.l10n.php), versioned in git and
    deployed with the theme. Content is translated in Polylang.
  - Custom post types: service, case_study (URL /work/), team_member and
    testimonial (no public URLs). All translatable. Details via simple meta
    boxes (no ACF dependency).
  - Project brief form: native handler (admin-post.php), nonce + honeypot +
    time trap + 5/hour/IP rate limit; emailed to the address in
    Customize → Agency & social (default hey@glittersocialmedia.gr). Nothing
    stored in the database.
  - Email delivery (TODO): WP Mail SMTP connected to the Google Workspace
    mailbox, so briefs are sent through Google and don't land in spam.

8. FRONT-END & DESIGN DECISIONS
=====================================================================

  - First version (sticker style: thick outlines, offset shadows, googly eyes)
    was judged too childish → rebuilt as a refined editorial agency look:
    off-white base, plum text, lilac section tints, hot pink used sparingly,
    hairline borders, soft motion. Disco ball kept as the single hero visual.
  - Fonts self-hosted (no Google Fonts requests → GDPR-friendly, faster):
    Fraunces (Latin display) + Piazzolla (Greek display) under one "Display"
    family via unicode-range; Manrope (Latin + Greek body). Only glyph sets a
    page needs are downloaded.
  - Plain CSS + vanilla JS, no build step; Lenis for smooth scroll (desktop
    only, disabled with reduced motion).
  - Accessibility: skip link, focus styles, reduced-motion support, all
    decorative SVGs aria-hidden, no horizontal scroll at 390px (tested).
